Remote desktop “hands & eyes” for computer use

Research note on giving the Marble harness remote control of a user’s real personal computer browser (and optionally the whole desktop) so the agent inherits existing logins, payment methods, and 2FA surface — without Marble implementing on-behalf-of (OBO) OAuth, vaulted cards, or per-site scrapers. Covers commercial products, open-source agents, build-vs-buy for Windows / Linux / macOS, and a concrete registration + tool design for Marble.

1. Goal fit (what you actually want)

The desired product is not “Marble opens a clean cloud browser and logs in as the user.” It is: Marble has remote hands and eyes on a machine the user already uses, so:

  • Amazon / airline / DoorDash / IRS / bank sites already show the user as signed-in.
  • Saved cards, Apple Pay / browser autofill, and device trust signals stay on the user’s machine.
  • 2FA and CAPTCHAs can often complete where the user’s browser is already trusted (or the user taps once on the same machine).
  • Marble itself never stores passwords, session cookies, or PANs if designed correctly.
Hard product truth: most “Computer Use” demos (OpenAI Operator / CUA cloud browser, Browserbase sandboxes, Anthropic’s Docker desktop demo) run in an isolated environment. They are great for general browsing and demos, but they do not inherit a personal Chrome profile unless you deliberately attach to one. For “order dinner with my saved card,” isolation is the wrong default.

Threat model (must design for this from day one)

  • Prompt injection — a page can contain text that tricks the agent into “click Buy” or “export cookies.” Anthropic’s own computer-use docs call this out explicitly.
  • Money movement — tickets, taxes, dinner are high-impact; need confirmations, allowlists, kill switch.
  • Remote access malware pattern — Tailscale + RDP is also a known attacker pattern; user-facing pairing must be deliberate (not a hard-coded auth key).
  • Site ToS / bot detection — pure pixel clicking looks human; CDP automation can look like automation. Both have tradeoffs.

2. Three architectural modes

Pick the mode first; product choice follows.

Mode Eyes Hands Inherits user auth? Best for
A. Browser-native (CDP / extension) DOM + accessibility tree + optional screenshot Click/type via Playwright/Puppeteer/CDP Yes if attached to real profile / live browser Web tasks (tickets, food, taxes portals)
B. Full desktop GUI Screenshot (vision) OS mouse/keyboard (xdotool, nut.js, robotgo, AX/UI Automation) Yes — whatever the user is logged into on that desktop Native apps + browser; hard UIs; “anything a human can click”
C. Cloud / VM browser Screenshot or DOM in remote Chrome Same, but remote No unless you sync profiles (painful / risky) Scraping, demos, multi-tenant SaaS agents
Marble target for personal computer use: primarily Mode A on the user’s machine (attach to their Chrome/Edge with existing cookies), with optional Mode B for OS dialogs, wallet extensions, desktop 2FA prompts, or non-browser apps. Mode C is a fallback when the user will not install a peer.

How Mode A actually inherits auth

  1. User’s Chrome/Edge is started (or already running) with remote debugging / CDP enabled, or
  2. Playwright / agent-browser connect_over_cdp attaches to http://127.0.0.1:9222, or
  3. Playwright MCP browser extension attaches to a selected profile / live tabs.

With raw CDP attach, the agent sees the default browser context — cookies, localStorage, extensions, and logged-in sessions. Isolated Playwright contexts deliberately do not.

Chrome has been tightening CDP attach to the default user data dir in some builds (community reports of “Google nuked our Playwright tool”). Practical workaround: dedicated debug profile that is a copy or secondary profile the user keeps logged in, or extension-based attach. Design for this fragility.

3. Commercial & frontier “computer use” landscape

3.1 Anthropic — Computer Use (API + Docker reference)

  • What it is: Claude models trained to emit screenshot-based actions (move mouse, click, type, scroll). API tool family computer_*.
  • Reference: open Docker demo (Ubuntu + XFCE + Firefox + VNC + Streamlit agent loop) using xdotool for input.
  • Auth inherit: partial — only what is inside the container/VM profile, not the user’s daily browser unless you build that.
  • Marble fit: reuse the action schema + loop ideas; do not depend on Anthropic hosting the user’s desktop. Any vision-capable model Marble already catalogs can drive similar tools if you implement the executor locally.

3.2 OpenAI — CUA / Operator → ChatGPT Agent; Responses “computer use”

  • Operator (2025) ran CUA against a remote virtual browser hosted by OpenAI — excellent for “do something on the web,” poor for “my Amazon account.”
  • Folded into broader ChatGPT Agent (visual browser + text browser + terminal) mid-2025; standalone Operator deprecated.
  • API (2026 docs): computer-use tool patterns in Responses API; guidance still assumes isolated browser/VM + human-in-the-loop for high-impact actions.
  • Codex Background Computer Use (2026): desktop-native background sessions (macOS-first narrative in industry writeups) — interesting, but product-locked and not a Marble-owned peer.
  • Marble fit: optional cloud Mode C if you later want hosted browsing; wrong primary for personal auth inheritance.

3.3 Google Gemini computer use

  • Industry 2026 comparisons place Gemini in a browser-anchored automation bet (vs Anthropic portable tools vs OpenAI desktop sessions).
  • Same inheritance caveat: unless automation runs on the user’s machine with their profile, tax/dinner logins are re-auth hell.

3.4 Browser infrastructure SaaS (Mode C)

ProductRoleAuth inherit personal PC?Notes
Browserbase Managed cloud Chrome + Stagehand / Director; CUA integrations No Great agent infra; profiles are their cloud profiles, not the user’s laptop cookies
Kernel Headful cloud browsers, long warm sessions, replays No Strong for durable remote sessions; not personal desktop

3.5 Local / “permissioned desktop” commercial agents

  • Lapu-style desktop agents: run on-device with OS accessibility APIs (AX on macOS, UI Automation on Windows); files and browser stay local. Closest commercial mental model to “hands on my PC,” but closed product — hard to embed as Marble tools without official APIs.
  • Bytebot-class “agent computer”: dedicated remote worker machine (VM/desktop the agent owns). Solves isolation and watchability; still not “my personal browser” unless that box is where the user lives.

Integration preference for Marble: do not embed a 50k-star Python agent into the harness process. Prefer a thin peer binary that speaks a small JSON protocol, optionally shelling out to Playwright / agent-browser / robotgo under the hood. Marble already patterns this with call_agent_process and MCP stdio servers.

5. Build your own peer agent (Win / Linux / Mac)

5.1 Recommended split: two capability layers

Layer 1 — Browser (primary)

  • CDP attach to user’s Chromium browser
  • Tools: navigate, snapshot (a11y tree), click role/text, type, wait, tabs, screenshot
  • Optional: export-free cookie use in place (never upload cookies to Marble server)

Covers ~90% of ticket / dinner / tax-portal tasks.

Layer 2 — OS desktop (secondary)

  • Screenshot + click coordinates + keystrokes
  • macOS: Accessibility permissions; Windows: UI Automation optional; Linux: X11/Wayland caveats
  • Use when CDP cannot touch OS dialogs, WebAuthn prompts, or native apps

Higher risk; gate with confirmations.

5.4 Why Go fits Marble

  • Same module / release pipeline as marble-harness.
  • robotgo for OS layer; chromedp or exec to Playwright for browser layer.
  • Single static-ish binary per GOOS/GOARCH in the existing GitHub Actions release matrix.

6. Integrating registration & tools with Marble

Goal: the agent in a Marble chat can say “open DoorDash and reorder last night’s meal” and tools route to the user’s peer, not a cloud browser. Keep secrets on the peer; Marble only sees screenshots and structured tool results.

6.1 Concepts

ConceptMeaning
computer / peerA registered endpoint (user laptop) with capabilities: browser, desktop, confirm
Registration token One-time code from Marble Settings → Computers; peer redeems over Tailscale/HTTPS
Binding Session or global default: which peer this chat may drive
Capability filter Like cap_images: only expose computer tools when a peer is online

6.2 Registration UX (operator)

  1. Settings → Computers → Add computer → generates 60s pairing code + install link.
  2. User installs marble-peer on Win/Mac/Linux; pastes code (or opens deep link).
  3. Peer stores long-lived device credential in OS keychain / DPAPI / libsecret — not in chat.
  4. Peer opens (or attaches) browser debug channel; reports capabilities + hostname.
  5. Marble UI shows green “Home-PC · browser online · desktop optional.”

6.3 Network options

Preferred: Tailscale (or similar mesh)

Marble and peer already on same tailnet. Peer listens on 100.x:port. No public ports.

Matches how many operators already reach Marble today.

Fallback: reverse tunnel

Peer dials out to harness WebSocket; harness never inbound-connects to home NAT.

Better for non-technical users without Tailscale.

6.4 Tool surface (proposed)

Expose a small, model-friendly set — either native tools or an MCP server shipped with the peer:

computer_list            → [{id, name, os, caps, online, last_seen}]
computer_bind            → {computer_id} | clear   # session default
computer_screenshot      → image attachment (multimodal) + meta {w,h}
computer_browser_tabs    → [{id, title, url}]
computer_browser_open    → {url} | new_tab
computer_browser_snapshot→ a11y / simplified DOM (text; cheap for LLM)
computer_browser_act     → {action: click|type|press|scroll|select, target, text?}
computer_desktop_act     → {action: click|type|key|move, x?, y?, text?}  # gated
computer_confirm         → {prompt, risk: low|money|auth} → waits for user UI on peer
computer_stop            → cancel in-flight peer actions

Multimodal already exists in Marble (ADR-0019): computer_screenshot can return a durable marble-att:// image into the session for vision models with cap_images.

6.5 Agent loop patterns

  • DOM-first: prefer browser_snapshot + role-based click (Browser Use / Playwright style) — more reliable than pixels.
  • Vision fallback: when snapshot fails (canvas, weird widgets), screenshot → model coordinates → desktop or CDP click.
  • Money gate: before any navigation matching /checkout|payment|submit|place.?order/i or peer-detected payment form, force computer_confirm.

6.7 Security controls (non-negotiable)

  • Domain allowlist / denylist per peer (e.g. allow *.doordash.com, deny */admin banking transfer paths until confirmed).
  • Human-in-the-loop for purchase, wire, tax file, password change.
  • No cookie export tools — agent acts in the browser; never GET /cookies into model context.
  • Session recording opt-in for dispute resolution; default off for privacy.
  • Kill switch on peer tray icon + Marble Stop turn cancels peer actions.
  • Rate limits on actions/min to slow runaway loops.
Do not implement “export passwords from Chrome and send to model.” That collapses the entire value proposition into a credential theft product. Act in place; confirm for money; log actions, not secrets.

6.8 Minimal schema sketch (SQLite, future ADR)

computers (
  id TEXT PRIMARY KEY,          -- slug
  display_name TEXT,
  device_pubkey TEXT,           -- peer auth
  os TEXT,                      -- windows|darwin|linux
  caps_json TEXT,               -- {browser,desktop,confirm}
  last_seen_at INTEGER,
  endpoints_json TEXT,          -- tailscale ip / ws path (no secrets)
  policy_json TEXT,             -- domain allow, require_confirm_money

session_computers (

7. Recommendations for Marble

Do this

  1. Product position: “Marble drives your browser on your PC” — not another Operator clone.
  2. Near-term (days): document CDP + Playwright MCP on the same host as Marble for power users (proof of value without peer).
  3. v1 (weeks): marble-peer browser-only over Tailscale reverse/WS; tools listed above; HITL for money; screenshot → multimodal.
  4. v1.5: optional OS desktop layer via robotgo for dialogs only.
  5. Defer: cloud Browserbase as primary; OBO OAuth to airlines; storing cards in Marble.

Buy / wrap vs build matrix

NeedWrap / useBuild
Reliable click/type in Chrome with logins Playwright CDP or agent-browser Thin RPC + policy + registration only
Vision click on arbitrary UI Anthropic/OpenAI computer-use schemas + any vision model Executor on peer (robotgo / xdotool)
Multi-tenant SaaS “agent browser” Browserbase / Kernel Don’t — wrong for personal auth story
End-user install experience — Tray app, pairing code, signed installers

What not to promise

  • 100% unattended tax filing without human confirm.
  • Bypassing bank step-up auth or WebAuthn without user presence.
  • That cloud CUA will “just use my Chrome passwords.”

8. Suggested phased roadmap (Marble-shaped)

  1. ADR draft — “Remote computer peer / computer use tools” (pair with this research).
  2. Spike: Playwright MCP + real Chrome profile on one machine; manual tool calls from chat.
  3. Protocol: peer WebSocket API + device auth; computer_list / screenshot / browser_act.
  4. UI: Settings → Computers; session bind chip; confirm modal on peer.
  5. Safety: domain policy, money confirm, audit events in SQLite.
  6. Desktop layer (optional) after browser path is trusted.
  7. Release artifacts: marble-peer-windows-amd64, darwin-arm64, linux-amd64 next to harness binaries.
Success metric for personal use: user says “reorder my usual Thai place” → peer opens already-logged-in site → user taps Confirm on peer for payment → done — with zero new passwords entered into Marble.
