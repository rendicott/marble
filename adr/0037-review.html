Search sessions

Type "android", land on the sessions where that work happened. The eye icon moves into Settings to make room.

Goal

  • A magnifying glass replaces #btn-prompt (the 👁 at index.html:249).
  • The system prompt and soul editor become a Settings tab (data-sec="prompt", rendered by the render() branch in settings.js).
  • The modal lists session id plus a short description as the operator types, including the session open right now, which may not be on disk yet.
  • "android" finds a session that only ever says "apk" and "gradle", through a small compiled-in alias table. No embeddings, no new dependency.

Locked

L1 The eye does not stay. Search takes the button.
Rec: replace #btn-prompt, remove #prompt-modal.
L2 System prompt becomes a Settings tab.
Rec: data-sec="prompt", reusing /api/prompt.
L3 Search scope is this harness.
Rec: one memory directory, including closed and system sessions.
L4 No embeddings service.
Rec: tokenize, stem lightly, expand through a hand-maintained alias table.

Open questions

Q1 What is the short description under the session id?
Rec: the clerk summary, falling back to the session title. A generated one-line blurb costs a model call per session and lags on live sessions. The title alone is weak, because deriveAutoTitle copies the latest user message, but it is always present and the operator may have renamed it.
Q2 What does the index store per session?
Rec: session_search_terms(session_id, term, count) in schema v14. Counts score "how much does this session mention apk". Positional postings and an FTS5 copy would duplicate the transcript for a phrase search the modal does not need. FTS5 is already compiled in, so it stays available later.
Q3 How is a session that is not on disk yet searched?
Rec: update the live session's term set in memory on each message append, merge it into SQLite on endTurn, and union it with the SQLite rows at query time. A full transcript scan per keystroke gets slow exactly on the long sessions this feature is for, and the daemon only flushes dirty sessions every few minutes.
Q4 How many results, and in what order?
Rec: 20 hits, match strength first, recency as the tiebreak. Pure recency buries an old session under today's chatter that happens to share a word. Pure strength buries the session the operator is in right now. No pagination in v1.
Q5 Which messages are indexed?
Rec: user and assistant carry the intent. Tool results are where "apk" and "gradle" actually appear in a build session, so excluding them breaks the motivating query — but they are also large and secret-adjacent, so scrub with config.ScrubSecrets and clip to 2 KiB. Thinking is noisy chain-of-thought and is excluded. tool_args_json is never indexed.
Q6 When does a query fire?
Rec: wait 150 ms after the last keystroke, and ignore queries shorter than 2 characters. A single character matches everything and teaches the operator nothing. Longer than 150 ms makes the modal feel dead while typing.
