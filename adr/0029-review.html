Reliable image attachments from URLs

Foundational harness work so agents can turn discovered image URLs into durable ADR-0019 attachment_ids in one step — without brittle shell/download chains. Client-agnostic (web UI, Wonderstand, API). Not a stock-photo product; not auto-Tavily injection.

Pain

Search/MCP returns image URLs → model cannot one-shot stage them → hotlinks or silence.

TodayGap
message_attach needs workspace path No first-class URL → bytes → attachment
web_fetch is HTML/JSON text Wrong tool for binary images
Screenshots / TTS already stage bytes Remote photos lack the same path
Markdown ![](https://…) hotlink Not durable; client-dependent; weak rights story

Open questions

Use rec / pick an option / write custom. Export saves 0029-answers.json (review-kit if loaded).

Q1Tool name
Rec: attach_from_url — verb matches outcome (attachment), not just fetch.
Q2LAN / private hosts
Rec: Allow LAN/private like web_fetch (home lab NAS photos); still block cloud metadata.
Q3Max redirects
Rec: 5 hops; re-validate host after each redirect.
Q4SVG via attach_from_url?
Rec: Reject SVG here (image sniff path). SVG stays document/`web_fetch`/inline fences — avoids XSS-as-image confusion.
Q5Provenance storage
Rec: meta_json on attachment row (source_url, fetched_at, optional credit/license).
Q6Batch URLs
Rec: Single URL in M1; optional urls[] max 4 in M3.
Q7URL → attachment cache
Rec: No cache in M1 (always new attachment); session hash(final_url) cache in M3 if needed.
Q8Vision / model re-inject
Rec: Follow existing ADR-0019 attachment / capability rules; don’t build a second multimodal pipeline in v1.
Q9HTTP API POST …/attachments/from_url
Rec: Yes in M2 (tests, scripts, non-agent clients). Tool-only is enough for M1.
Q10Default max download bytes
Rec: 8 MiB, not exceeding ADR-0019 image max if configured lower.
