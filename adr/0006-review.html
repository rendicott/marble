Yes — MCP to Tavily is the mainstream easy path. Hermes also offers native Tavily-backed tools; MCP is how you stay vendor-pluggable and get extract/research tools without shipping them in Marble.

Ecosystem refs: Tavily MCP docs, Goose Tavily extension, OpenCode Tavily vs SearXNG MCP comparisons, Hermes dual native+MCP path.

2. Decision

  • Marble becomes an MCP client
  • Discover + call tools, resources, prompts
  • stdio + HTTP/SSE transports in v1
  • Merge tools into ADR-0005 loop with mcp_* names
  • Config file + env secrets; fail soft if a server dies

Out of scope

  • Marble as MCP server
  • OAuth / multi-user remote MCP
  • Native hardcoded Tavily client (later optional)
  • Sampling (server → host LLM)
  • Browser/CDP automation

4. Config (Cursor-compatible shape)

Primary file: $MEMORY/mcp.json · override --mcp-config · kill switch --mcp-disable

{
  "mcpServers": {
    "tavily": {
      "command": "npx",
      "args": ["-y", "tavily-mcp@latest"],
      "env": { "TAVILY_API_KEY": "${TAVILY_API_KEY}" },
      "enabled": true
    }
  }
}
MCP children run as the harness user. Stdio servers are as trusted as shell_execute. Pass only explicit env keys; never dump the whole environment by default.

5. Web search recipe (docs, not core)

  1. Get a Tavily API key (or stand up SearXNG + its MCP).
  2. Export TAVILY_API_KEY.
  3. Write ~/.marble/mcp.json as above.
  4. Restart Marble → health shows MCP servers → model sees mcp_tavily_… tools.

If MCP overhead is painful for the single-tool case, a later ADR can add a thin native web_search without removing MCP.

6. Implementation phases

  1. Config parse + env expand
  2. Stdio JSON-RPC: initialize; list tools/resources/prompts
  3. HTTP/SSE transport (same capability surface)
  4. Catalog → ToolSpec + namespacing + resource/prompt surface
  5. call/read/get + 60s timeout + merge Execute
  6. Health chip + shutdown cleanup
  7. Docs + mock-server tests

7. Questions (all locked)

All Q1–Q15 locked. Answers: 0006-answers.json. ADR Accepted.

Config & shape

Q1 Config file location?
Rec: $MEMORY/mcp.json + --mcp-config override.
Q2 Config shape?
Rec: Cursor/Claude-compatible mcpServers map.
Q3 Tool name prefix?
Rec: mcp_<server>_<tool> sanitized to [a-zA-Z0-9_].

Protocol & scope

Q4 Transports in v1?
Rec: stdio only; Streamable HTTP/SSE later.
Q5 Native web_search in same ADR?
Rec: no — deliver search via MCP (Tavily recipe).
Q6 MCP tools when limp mode?
Rec: yes — independent of DB.
Q7 Per-session MCP vs process-global?
Rec: process-global connections; available to all sessions.
Q11 Resources / prompts in v1?
Rec: no — tools only.

Safety & limits

Q8 Server allow policy?
Rec: explicit enabled per server; operator-authored config only.
Q9 Max MCP tools registered?
Rec: soft cap 64; log + skip overflow.
Q10 Default tool call timeout?
Rec: 60s (align shell default).
Q14 Fail harness start if MCP fails?
Rec: no — degrade; surface in health.
Q15 Drop built-ins when MCP overlaps?
Rec: keep built-ins; namespacing avoids collision.

UX & implementation

Q12 UI for MCP status?
Rec: health JSON + small chip; settings UI later.
Q13 Go MCP library strategy?
Rec: maintained client if lean; else in-tree minimal JSON-RPC for tools only.
