1. Goal

Make Marble a practical coding + sysadmin harness:

  • Navigate and edit code with structure (not only full-file write)
  • Run shell with operator-tunable power
  • Long jobs via background tasks + continuations
  • Intentional memory + skills for learn-over-time
  • Loop that warns then stops, instead of silent thrash

Out of scope

  • Vector RAG / embeddings
  • True OS sandbox (bwrap/nsjail)
  • MCP bridge, multi-user auth
  • Interactive PTY / language-aware summary
  • Settings UI for shell (DB seed enough v1)

3. Agent loop (detailed)

user / continuation → begin turn loop: inject soft advisories if thresholds crossed trim history to budget model(+tools) if tool_calls: for each tool (serial v1): policy check → execute → append result rounds++ if rounds ≥ 65: advisory if rounds ≥ 80: STOP if wall ≥ 3m: advisory continue else final assistant → end turn

Advisories (Q6)

  • Ephemeral notes for the model each call
  • UI: collapsible harness chips
  • Omit from session Markdown
  • Keep in DB session_events
  • Throttle: on threshold cross + periodic

Auto-compaction (Q3/Q4)

  • Primary: model calls session_compact
  • Auto if ≥85% for 3 consecutive rounds
  • LLM summary via system agent (daemon-scheduled)
  • System agent visible in bottom left-pane list
edit_file rule: requires a successful file_read on the same path earlier in the same turn. Harness enforces; model cannot skip.

5. Shell security model ⚠

This is the highest-risk surface. Deny lists are best-effort, not a sandbox. Privilege never exceeds the parent marble-harness process (same UID/GID). If you run Marble as root, the agent is root — don’t.

Hard guarantees (OS)

  • Child inherits harness credentials
  • No setuid / no added capabilities
  • Process group kill on timeout

Policy layer (Marble)

  • Master switch shell_enabled
  • Mode: deny_list (default) or allow_list (lockdown)
  • Patterns stored in DB settings (editable, survives restart)
  • cwd jailed to workspace when strict
  • Timeouts: default 60s, max 300s
  • Configurable weak → powerful via settings

Seed deny examples

rm -rf / , mkfs, dd of=/dev/
sudo, su, pkexec, doas
shutdown, reboot, poweroff
(optional) writing --memory paths

Settings keys

shell_enabled
shell_mode                 # deny_list | allow_list
shell_deny_patterns        # JSON regex[]
shell_allow_patterns
shell_default_timeout_sec  # 60
shell_max_timeout_sec      # 300
shell_max_output_bytes     # 512KiB
shell_cwd_strict           # true
shell_block_memory_paths   # true

6. Background tasks & continuations

BG tasks

  • Per-session registry; task_id returned
  • Same shell policy as shell_execute
  • check / kill / list
  • Rec: max 8 concurrent per session
  • Rec: not survive harness restart (orphan on boot)
  • On session close: TERM → KILL all session tasks

schedule_continuation

  • Required prompt re-injected at fire time
  • delay_sec and/or wait_for_task
  • Starts a new agent turn if session idle
  • Rec: max delay 24h; cancel on close
  • Rec: persist schedules to DB (normal mode)
  • UI: pending continuation chip
# long build pattern
start_background_task(command="make release")
schedule_continuation(
  delay_sec=30,
  wait_for_task="<id>",
  prompt="Build finished or timed slice elapsed — check_background_task and report."
)
